## 4. Sessions, reruns and the single gating call
- One GPU session run by the human (runbook `reports/p2r/GPU_RUNBOOK_P2R.md`), the **same GPU type as P2 (RTX PRO 6000)**, hard budget **INR 700 including set-up**: an instance shutdown timer armed at login, the driver's minute budget computed from what is left, and the manual dashboard stop rule. Whether an OS shutdown stops billing is checked in the dashboard at the first stop.
- First complete run per model counts (P2 section 1).
- **Rerun rule.** After the session, the human decides on a second session **from the session logs only** (driver log, `log.jsonl` events, manifests, deviation files), never from chunks or any analysis output. A second session is allowed once, for each model that is MISSING (incomplete: budget or crash) or MISSING (not run: the session stopped before it, e.g. a pilot FATAL, or it failed the patching tests of section 3), within a budget the human states in the same note. If a code change is needed (e.g. a loader fix for a new architecture), it follows this order: (1) a deviation naming the failure (from the logs), the files changed and the diff is committed before the change; (2) the change touches only model loading or device handling, never measurement, materials, outcomes or analysis; (3) on CPU, through the ledger and at the standing cap, the frozen pytest passes with the changed code, and the driver's smoke command (`run_p2.py` on pythia-70m, 5 facts × 2 paraphrases) exits 0 with both the code at `prereg-P2R` and the changed code and gives identical output values (P2 kept no smoke outputs, so the comparison is between the two code versions); (4) the changed code is committed and tagged `prereg-P2R-fix1`, with a sha256 file of the changed files named in the deviation, before the second session, which checks out that tag (runbook section E). A model MISSING (insufficient data) or MISSING because its files differ from the pins is never rerun.
- **The P2R gating call (`p2r_analysis.py --set correct`) runs exactly once**, after (i) all P2R sessions have ended and (ii) the human's rerun decision is committed. No P2R analysis of any kind (including partial, per-model or exploratory) runs before that. Right before the gating call, `check-cache --only-present` runs on the local tokenizer cache through the ledger and must print OK (the analysis reads tokenizer files for covariates); if it does not, the tokenizer files are restored from the pinned commit and the check repeated before the call. If a second session runs, the gating call uses each model's first complete run across the sessions. If the gating call ends without writing `p2_decision.json` (a crash or a kill, e.g. at the memory cap), it is run again with identical code, inputs and seed; every attempt is logged in the ledger, and only an attempt that wrote `p2_decision.json` counts.
- Deviation files written by the driver in a P2R session are installed under `prereg/deviations/`; the session UTC identifies them.

## 5. Claims, pooling and wording
**Mapping to the P2R decision file (`p2_decision.json` of the single gating call).** For a model and a headline rule, PASS = the rule's predicate is `True`; FAIL = `False`; MISSING = the predicate is `None` (an input MISSING: failed fit, failed null, failed MoM), or the model's `status` is not `ok`, or the model is absent. Predicates (frozen `decide()` fields): fact share > 0 = `null_lt_0.01`; H1 = `H1`; H1-alt = `H1_alt`; no fixed layer = `icc1_upper_lt_0.15`; it takes N paraphrases = `H1` and `nprime_ge_8` (MISSING if either is `None`, FAIL if either is `False` and neither `None`); wording shifts together = `H1` and `tf_gt_resid_D1` (same rule); fact depth unexplained = `H1_alt`.

**(a) Replication test (confirmatory; data unseen).** Every P2 headline rule (P2 section 6) is evaluated with the frozen ">= 2 families" requirement over the two P2R families: a rule holds in the replication only if it is PASS in **both** Gemma and Mistral. With two families the conflict rule cannot trigger (H1 and H1-alt require opposite MoM signs within a model). Primary replication target: "The fact share is above zero".

**(b) Four-family summary (preregistered; NOT independent).** `p2r_combine.py` over Llama-3.1-8B, OLMo-2-1124-7B, Gemma-2-9B, Mistral-7B-v0.1.
- It is partly decided in advance. "The fact share is above zero" is already licensed by Llama and OLMo, so it is licensed in the summary whatever P2R shows. Llama already meets H1 with n′ = 8, so one new family meeting H1 licenses "H1 holds" and, if that family's n′ ≥ 8, "it takes N paraphrases" in the summary; "wording shifts together" still needs two new families (Llama's `tf_gt_resid_D1` is False), and H1-alt sentences need two new families (H1-alt holds in no P2 model). Its error rate is therefore higher than P2's design figure: for a false H1-dependent licence when H1 is false in both new models, at least about 0.05 (nominal) instead of about 0.006, and possibly up to about 0.2, since the P2 robustness simulation found the single-measure H1 interval condition passing in 0.050–0.120 of null datasets (the full H1 condition was not simulated).
- **Rule:** a sentence licensed only by (b) never appears in the abstract, a contribution bullet, a heading or the conclusion; it is reported only in the results section as a per-family tally, "k of 4 families (2 analysed before this amendment)", using the output's per-rule family lists.

**(c) Wording (exhaustive; every outcome, every paper location).** Paper locations of the P2 headline sentence (as committed at the tag `prereg-P2R`): **L1** the abstract sentence beginning "In a separate study of Llama-3.1-8B and OLMo-2-1124-7B"; **L2** the second contribution bullet; **L3** the Study-2 results paragraph "The fact share is above zero; separating answer identity lowers it"; **L4** the Discussion paragraph "What the licensed sentence says"; **L5** the Conclusion. Every added sentence that states a result carries "on correctly answered prompts", and every Lg that states a result carries "which includes answer-token identity" (R6 and the Limitations sentences state no result). A FAIL is worded as "the preregistered test did not show …", never as an absence (P2 section 6: otherwise the estimates are reported as an intermediate result, here in the L3 table). MISSING reasons are named exactly as one of: "too few correct answers" (inclusion rule failed), "the run did not complete" (incomplete: budget or crash), "it was not run" (the session stopped before it, or it failed or lacks the patching tests of section 3), "a preregistered input of the test failed" (predicate `None`: failed fit, null or MoM), "its model files differed from the preregistered ones" or "its model files could not be verified" (section 1). The reason is read from the session logs, the provenance files and the decision file, never chosen.

The outcome then enters the next version under the obligation above.
- When the outcome is available, it enters through `scripts/make_numbers.py` and the gate process (G6), with the wording of section 5(c).
